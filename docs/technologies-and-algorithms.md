# 技术与算法详解

Sixel-Web 项目涉及的核心技术、算法和协议的详细说明。

---

## 1. Sixel 协议

### 1.1 概述

Sixel 是 DEC（Digital Equipment Corporation）在 1980 年代为 VT340 终端定义的位图图形协议。它将图像编码为 ASCII 文本流，可直接嵌入终端输出中。

### 1.2 协议结构

```
ESC P q [光栅属性] [颜色定义] [Sixel 数据] ESC \
```

- **DCS 头**：`ESC P q`（7-bit）或 `0x90 q`（8-bit），标识 Sixel 数据开始
- **光栅属性**：`"Pan;Pad;Ph;Pv`，声明像素宽高比和图像尺寸
- **颜色定义**：`#N;2;R%;G%;B%`，定义调色板颜色（RGB 百分比）
- **Sixel 数据**：每 6 行像素为一个 band，每列用一个字符（`?`~`~`）编码 6 个像素的位掩码
- **控制字符**：`$`（回车到行首）、`-`（换行到下一个 band）
- **RLE 压缩**：`!Nc` 表示字符 `c` 重复 N 次
- **ST**：`ESC \`，标识 Sixel 数据结束

### 1.3 Sixel 字符编码

每个 Sixel 字符代表 6 个垂直像素的位掩码，加上 0x3F 偏移：

| 字符 | ASCII | 位值 | 二进制 | 含义 |
|------|-------|------|--------|------|
| `?`  | 63    | 0    | 000000 | 无像素亮起 |
| `@`  | 64    | 1    | 000001 | 仅第 1 行 |
| `A`  | 65    | 2    | 000010 | 仅第 2 行 |
| `_`  | 95    | 32   | 100000 | 仅第 6 行 |
| `~`  | 126   | 63   | 111111 | 所有 6 行 |

### 1.4 兼容性

| 终端 | Sixel 支持 | 备注 |
|------|-----------|------|
| Windows Terminal | ✅ | Windows 10+ |
| WezTerm | ✅ | 跨平台 |
| xterm | ✅ | 需编译时启用 |
| kitty | ✅ | 原生支持 |
| iTerm2 | ✅ | macOS |
| GNOME Terminal | ❌ | 不支持 |
| Alacritty | ❌ | 不支持 |

## 2. 颜色量化

颜色量化将图像从数百万色压缩到有限调色板（通常 256 色），是 Sixel 编码的核心步骤。

### 2.1 Median Cut（中位分割）

默认量化算法，来自 netpbm 库的 pnmcolormap 实现。

**原理**：
1. 将所有颜色放入一个"盒子"
2. 找到范围最大的维度（按亮度加权：R×0.299, G×0.587, B×0.114）
3. 按该维度排序，在像素数中位数处分割为两个盒子
4. 重复直到盒子数量等于目标颜色数
5. 每个盒子的加权平均色作为调色板颜色

**优化**：
- 15-bit 哈希直方图（`Uint16Array(32768)`）替代 Map，零 GC 开销
- 大图采样 50,000 像素构建直方图，调色板质量不受影响
- 亮度加权维度选择，更符合人眼感知

**适用场景**：通用场景，速度快，质量可接受。

### 2.2 PNN（Pairwise Nearest Neighbor）

高质量量化算法，来自 chafa 终端图形库。

**原理**：
1. 每个唯一颜色初始化为一个 bin
2. 迭代合并距离最近的两个 bin，直到 bin 数量等于目标颜色数
3. 合并距离 = `像素数之积 × 色彩距离²`
4. 使用 15-bit 预量化减少初始 bin 数量（最大 32768）

**与 Median Cut 的区别**：
- Median Cut 按空间范围分割，PNN 按颜色相似度合并
- PNN 在颜色密集区域（渐变、肤色）表现更好
- PNN 速度较慢，仅在 high 质量模式下使用

**适用场景**：对色彩还原要求高的照片。

### 2.3 色彩空间与感知

人眼对不同颜色通道的敏感度不同（ITU-R BT.601）：

```
亮度 = 0.299 × R + 0.587 × G + 0.114 × B
```

绿色最敏感，蓝色最不敏感。量化时按此权重选择分割维度，确保调色板分配符合人眼感知。

## 3. 抖动算法

### 3.1 无抖动

直接将每个像素映射到最近的调色板色。结果是硬边色带（color banding），在渐变区域尤其明显。

### 3.2 Bayer 有序抖动

在量化**前**叠加一个 8×8 的阈值矩阵，让相邻像素的量化结果产生微小差异。

```
Bayer 8×8 矩阵（值域 0-63，归一化后 -0.5 ~ +0.5）：
┌────┬────┬────┬────┬────┬────┬────┬────┐
│  0 │ 32 │  8 │ 40 │  2 │ 34 │ 10 │ 42 │
│ 48 │ 16 │ 56 │ 24 │ 50 │ 18 │ 58 │ 26 │
│ 12 │ 44 │  4 │ 36 │ 14 │ 46 │  6 │ 38 │
│ 60 │ 28 │ 52 │ 20 │ 62 │ 30 │ 54 │ 22 │
│  3 │ 35 │ 11 │ 43 │  1 │ 33 │  9 │ 41 │
│ 51 │ 19 │ 59 │ 27 │ 49 │ 17 │ 57 │ 25 │
│ 15 │ 47 │  7 │ 39 │ 13 │ 45 │  5 │ 37 │
│ 63 │ 31 │ 55 │ 23 │ 61 │ 29 │ 53 │ 21 │
└────┴────┴────┴────┴────┴────┴────┴────┘
```

**特点**：
- 并行处理，速度快
- 产生规则的网格纹理，在暗部渐变区域可见
- 不依赖量化结果

**适用场景**：对速度要求高、可接受轻微网格纹理的场景。

### 3.3 Floyd-Steinberg 误差扩散

在量化**后**，将每个像素的量化误差按固定权重传播到相邻像素。

```
权重分布（libsixel 标准）：
        当前    7/16 →
 3/16 ↙  5/16 ↓  1/16 ↘
```

**处理流程**：
```
对每个像素 (x, y):
  1. 取原始值（含累积误差）
  2. 查找最近调色板色 → 计算误差 = 原始值 - 调色板色
  3. 将误差按权重加到相邻像素的误差缓冲区
```

**与 Bayer 的关键区别**：
- FS 是**自适应**的：误差根据实际量化结果动态传播
- Bayer 是**固定**的：无论量化结果如何，阈值矩阵不变
- FS 在暗部渐变和平滑过渡上远优于 Bayer
- FS 是**串行**处理（每像素依赖前序像素的误差），无法并行化

**性能优化**：使用 15-bit R5G5B5 哈希缓存表（`Uint16Array(32768)`），首次查找 O(256)，后续 O(1)。

**适用场景**：默认推荐，尤其适合照片和渐变图像。

### 3.4 自动禁用

当原始图像的唯一色数 ≤ 调色板大小时（如 200 色图片 + 256 色调色板），量化本身无损，FS 不会产生额外收益，自动跳过以节省计算。

## 4. Sixel 编码策略

### 4.1 RLE（Run-Length Encoding）

Sixel 协议支持 RLE 压缩：`!Nc` 表示字符 `c` 重复 N 次。

**阈值优化**：`!Nc` 格式本身需要至少 3 字符（`!` + 数字 + 字符）。当重复次数 ≤ 3 时，逐字输出更短：

| 重复次数 | 逐字输出 | RLE 输出 | 选择 |
|---------|---------|---------|------|
| 1 | `?` (1字节) | `!1?` (3字节) | 逐字 |
| 2 | `??` (2字节) | `!2?` (3字节) | 逐字 |
| 3 | `???` (3字节) | `!3?` (3字节) | 相同 |
| 4 | `????` (4字节) | `!4?` (3字节) | RLE |
| 200 | 200字节 | `!200?` (5字节) | RLE |

### 4.2 6 行带打包

Sixel 协议每列用 6 位编码 6 个垂直像素。编码器将图像按 6 行一组打包，每列输出一个 Sixel 字符。

### 4.3 DCS 头格式

- **7-bit**：`ESC P q`（`\x1bPq`）— 默认，兼容性最好
- **8-bit**：`0x90 q`（`\x90q`）— 老式终端，单字节 DCS

### 4.4 光栅属性

`"Pan;Pad;Ph;Pv` 声明图像元数据：
- Pan/Pad：像素宽高比（通常 1:1）
- Ph：图像宽度（像素）
- Pv：图像高度（像素）

## 5. 量化质量模式详解

### 5.1 auto（平衡）

| 参数 | 值 |
|------|-----|
| 量化算法 | Median Cut |
| 抖动模式 | 用户选择（默认 Floyd-Steinberg） |
| 调色板颜色数 | 用户选择（默认 256） |
| 分辨率 | 用户选择 |
| 直方图采样 | 50,000 像素 |

**处理流程**：
```
原图 → [Bayer 可选] → Median Cut 量化 → [FS 可选] → Sixel 编码
```

**适用场景**：日常使用，速度与质量平衡。

### 5.2 low（快速）

| 参数 | 值 |
|------|-----|
| 量化算法 | Median Cut |
| 抖动模式 | 用户选择 |
| 调色板颜色数 | 用户选择 |
| 分辨率 | 用户选择 |
| 直方图采样 | 50,000 像素 |

**与 auto 的区别**：当前实现与 auto 相同。未来可进一步降低采样数或使用更快的量化策略。

**适用场景**：大批量处理、预览用途。

### 5.3 high（高质量）

| 参数 | 值 | 说明 |
|------|-----|------|
| 量化算法 | **PNN** | 更精确的调色板，渐变和肤色更好 |
| 抖动模式 | **Floyd-Steinberg** | 若用户未选择抖动，自动启用 FS |
| 调色板颜色数 | **256** | 强制最大颜色数 |
| 分辨率 | **原始** | 不缩放，保持原图尺寸 |
| 直方图采样 | **无** | 使用全量像素，保证 PNN 精度 |

**处理流程**：
```
原图 → PNN 量化（全量） → Floyd-Steinberg 误差扩散 → Sixel 编码
```

**适用场景**：对色彩还原要求高的照片、需要与 img2sixel 质量对标的场景。

**性能代价**：PNN 比 Median Cut 慢约 2-5 倍，FS 比无抖动慢约 1.5 倍。大图（>2000px）可能需要数秒。

## 6. 编码策略详解

### 6.1 auto（平衡）

| RLE 阈值 | 策略 |
|----------|------|
| ≥ 4 | 使用 RLE 压缩（`!Nc`） |
| < 4 | 逐字输出 |

**原理**：RLE 阈值为 4，即连续 4 个以上相同字符才压缩。这是 libsixel 的标准策略，在文件体积和编码速度之间取得平衡。

**适用场景**：默认选择，适合绝大多数场景。

### 6.2 fast（跳过 RLE）

| RLE | 策略 |
|-----|------|
| 完全跳过 | 所有 Sixel 字符逐字输出 |

**原理**：跳过 RLE 压缩，直接输出原始 Sixel 字符序列。编码速度最快，但输出文件体积最大。

**适用场景**：
- 实时预览（需要最快编码速度）
- 终端直出（文件体积不重要）
- 调试编码问题

### 6.3 size（更小体积）

| RLE 阈值 | 策略 |
|----------|------|
| ≥ 2 | 使用 RLE 压缩 |
| < 2 | 逐字输出 |

**原理**：RLE 阈值降为 2，即连续 2 个以上相同字符就压缩。输出文件体积最小，但编码稍慢（更多 RLE 操作）。

**适用场景**：
- 需要最小化 .six 文件体积
- 网络传输场景
- 存储空间敏感

### 6.4 体积对比示例

以 1863×1290 像素的照片为例：

| 策略 | 典型体积 | 相对大小 |
|------|---------|---------|
| fast | ~2.5 MB | 100% |
| auto | ~1.9 MB | ~76% |
| size | ~1.7 MB | ~68% |

## 7. 兼容性选项

### 7.1 8-bit DCS

Sixel 协议的 DCS（Device Control String）引入序列有两种形式：

| 形式 | 字节 | 说明 |
|------|------|------|
| 7-bit（默认） | `ESC P` (`\x1bP`) | 两个字节，现代终端均支持 |
| 8-bit | `0x90` | 单字节，VT240 等老终端使用 |

**何时启用**：仅当目标终端是 VT240 或类似老硬件时需要。现代终端默认使用 7-bit。

### 7.2 GRI ≤ 255

GRI（Graphics Repeat Introducer）是 Sixel 的 RLE 压缩命令 `!Nc`。

| 参数 | 默认行为 | GRI ≤255 |
|------|---------|----------|
| N 范围 | 1 ~ 65535 | 1 ~ 255 |
| 超长重复 | 单个 `!Nc` | 拆分为多个 `!255c` |

**何时启用**：仅当目标终端限制 GRI 参数 ≤ 255 时需要（如 VT240）。现代终端无此限制，启用后仅增加少量文件体积。

## 8. 文件加密

### 8.1 加密算法

使用 **AES-256-GCM**（Galois/Counter Mode）进行认证加密，同时提供：
- **机密性**：数据加密后不可读
- **完整性**：GCM 认证标签检测篡改

密钥通过 **PBKDF2**（Password-Based Key Derivation Function 2）从用户密码派生：
- 迭代次数：100,000（OWASP 推荐最低值）
- 哈希算法：SHA-256
- Salt：16 字节随机值（每次加密不同）
- 输出：256-bit AES 密钥

### 8.2 加密文件格式

```
┌──────────┬──────────┬──────────┬─────────────────────┐
│ Magic    │ Salt     │ IV       │ Encrypted Sixel Data│
│ 4 bytes  │ 16 bytes │ 12 bytes │ N bytes             │
│ "SXL1"   │ PBKDF2   │ AES-GCM │ 密文 + Auth Tag     │
└──────────┴──────────┴──────────┴─────────────────────┘
```

- **Magic** `SXL1`（`0x53 0x58 0x4C 0x31`）：标识文件为加密格式
- **Salt**：PBKDF2 密钥派生用的随机盐
- **IV**：AES-GCM 初始化向量（每次加密随机生成）
- **Encrypted Data**：加密后的 Sixel 数据 + 16 字节 GCM 认证标签

### 8.3 密码处理

- 密码通过 `TextEncoder` 编码为 UTF-8 字节，支持任意字符（中文、emoji、特殊符号等）
- 密码不持久化，不存入 localStorage，页面刷新后清空
- 批量解密时，首个加密文件弹窗输入密码后自动缓存，后续文件复用

### 8.4 随机密码生成

使用 `crypto.getRandomValues` 生成 16 位密码学安全随机密码：

- 字符集：62 个字符（`A-Z` 去 `I/O`，`a-z` 去 `l/o`，`2-9` 去 `0/1`，`!@#$%&*`）
- 排除易混淆字符减少输入错误
- 熵值：`log2(62^16) ≈ 95 bits`
- 生成后自动显示明文，方便用户复制

### 8.5 剪贴板复制

使用 `navigator.clipboard.writeText()` API 将密码复制到系统剪贴板。复制成功后按钮短暂变为 ✅ 确认。

### 8.6 浏览器兼容性

使用 Web Crypto API（`crypto.subtle`），支持：
- Chrome 37+、Edge 12+、Firefox 34+、Safari 11+
- 需要 HTTPS 或 localhost（`crypto.subtle` 在非安全上下文中不可用）

## 9. 批量处理与 ZIP

### 9.1 文件夹选择

使用 `<input webkitdirectory>` 属性实现文件夹递归扫描。浏览器会递归获取文件夹内所有文件，每个文件带有 `webkitRelativePath` 属性保留相对路径。

**文件过滤**：
- 编码：`.png` `.jpg` `.jpeg` `.gif` `.bmp` `.webp`
- 解码：`.six` `.sixel` `.txt`

### 9.2 ZIP 读写

**写入器**（~120 行）：
- Store 模式（无压缩），零外部依赖
- 支持 UTF-8 文件名（flag bit `0x0800`）
- CRC32 校验

**读取器**（~80 行）：
- 支持 Store（未压缩）和 Deflate（压缩）
- Deflate 使用浏览器原生 `DecompressionStream` API
- 兼容 Chrome 80+、Edge 80+、Firefox 113+、Safari 16.4+

## 10. 性能优化技术

### 10.1 15-bit 哈希直方图

将 24-bit RGB 颜色量化到 15-bit（R5G5B5），每个通道取高 5 位：

```javascript
var hash = ((r >> 3) << 10) | ((g >> 3) << 5) | (b >> 3);
```

- 哈希空间：2^15 = 32,768 个桶
- 存储：`Uint16Array(32768)` = 64 KB，在 L1 缓存内
- 直接索引，无哈希冲突

### 10.2 FS 颜色查找缓存

FS 误差扩散中每个像素需查找最近调色板色。使用 15-bit 哈希缓存：

```
首次:  遍历 256 色 → 写入 cache[hash]
后续:  cache[hash] → O(1) 命中
```

自然图像中相邻像素颜色高度相似，缓存命中率 > 95%。

### 10.3 直方图采样

Median Cut 对直方图采样 50,000 像素构建调色板。由于量化本身是近似算法，采样不影响最终调色板质量，但将直方图构建从 O(像素数) 降到 O(50000)。

### 10.4 亮度加权维度选择

Median Cut 分割时，按 ITU-R BT.601 亮度权重选择维度：

```javascript
var lumR = rangeR * 0.299;
var lumG = rangeG * 0.587;  // 绿色权重最高
var lumB = rangeB * 0.114;
```

确保调色板分配符合人眼对亮度的敏感度。
